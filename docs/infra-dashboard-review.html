Making the Infra Dashboard a real observability tool

A review of the Infra Dashboard Prototype as it exists in export.ndjson — your five observations evaluated, the corrections I'd make, the gaps I'd fill, and a mock-up of where it should land.

Object: 1 dashboard · 19 panels Sources: metrics-* · servicenow-incidents-* Reviewed: 4 Sep 2026 Verdict: solid skeleton, needs hardening

Executive summary

The prototype is a good skeleton pointed at the right data — but it isn't yet safe to run a NOC on

It already pulls from the two sources that matter (system metrics and ServiceNow incidents) and the CPU/memory heat tables are genuinely useful. The problems are that the "up / down / availability" numbers depend on settings the dashboard doesn't pin down, the incident panel isn't proven to be about infrastructure at all, two of the six sections are empty placeholders, and the whole thing has no filters, no history, and no auto-refresh.

Evaluating your observations

Your five notes, assessed

Short version: every one of them is valid. Two (incidents and the detailed-dashboard links) need a fact from the live environment before they can be closed out — I've marked those clearly.

01 Server Down window: now-5m → now-15m You suggested widening the window so a restart isn't counted as down. Agree▸

Confirmed and correct. In the export, Servers Up counts hosts with @timestamp >= now-5m, and Servers Down = total hosts − hosts seen in the last 5m. System metrics typically scrape every 10–60s, so a reboot, an agent restart, or a short ingest hiccup easily crosses a 5-minute line and flips a healthy host to "down."

Recommendation: move to now-15m as you suggest — it's comfortably longer than a normal collection gap but still tight enough to catch a real outage. While you're in there, make the syntax consistent: "Servers Up" uses quoted "now-5m" while "Servers Down" and "Availability" use unquoted now-5m. Pick one.

02 "Fleet" → "Server Availability" You want the "Fleet Availability %" tile renamed. Agree▸

Agree. The tile is labelled Fleet Availability % while the section header above it already says Servers Availability — so the page contradicts itself. "Fleet" is also ambiguous to anyone outside the team.

Recommendation: rename the tile to Server Availability % so the label and the section agree. (This is a cosmetic fix; the number it produces still has the deeper issue in correction C3 below.)

03 P1/P2/P3 incidents — are these actually infrastructure? Filters like priority_name : "2 - High" work, but you couldn't tie the incidents to a host. Agree · needs a data answer▸

This is the sharpest observation, and it's right. The three tiles run count() on servicenow-incidents-* filtered only by priority_name — there is no host, CI, or category filter. Nothing in the panel constrains it to servers, so it will happily count application, network, or service-desk tickets too. In the export, the incidents index also carries no host.* field at all, which is exactly why you couldn't relate a record to a host.name in Discover.

What to confirm: in Discover on servicenow-incidents-*, look for a CI/asset field — commonly cmdb_ci, cmdb_ci.name, ci.name, u_host, or a category like category: "Server".

Then decide: if such a field exists, add a filter (e.g. cmdb_ci : * plus an infra category) so the panel is genuinely infrastructure incidents. If it doesn't, this panel can't claim to be infra — relabel it honestly as ServiceNow Incidents (all) and move it, or drop it from an infra dashboard. Don't leave it implying something the data can't back.

04 Oracle tab: Dashboard 1 / 2 / 3 all point to the same place You asked whether that's intended and want them renamed to their function. Agree▸

Confirmed in the export: under Oracle Servers, all three links — Dashboard 1, Dashboard 2, Dashboard 3 — resolve to the identical URL (…/app/r/s/tf0R3, "Prototype Infrastructure Dashboard KPIs"). As written they're placeholders, not three destinations.

Recommendation: this is almost certainly unintended. Either wire each to the dashboard it's meant to open and rename it to what it shows (e.g. "Oracle — Tablespace & Sessions", "Oracle — Wait Events"), or collapse to a single correctly-named link until the others exist. A link named "Dashboard 2" tells the reader nothing.

05 MySQL tab: same duplicate links as Oracle Same three-links-one-URL problem under MySQL. Agree▸

Same finding, same fix. The MySQL section's three "Detailed Dashboards" links are identical to Oracle's and point to the same tf0R3 URL. Treat it exactly as note 4: give each link a real destination and a functional name, or reduce to one.

Worth adding: both the Oracle and MySQL sections contain only these links — no metrics of their own. See correction C6: those two tiers are effectively unmonitored on this dashboard today.

Enhancements · things not on the dashboard yet

The prototype answers "how many servers are up and how many tickets are open." A real infra dashboard also answers which ones, since when, is it getting worse, and am I even still receiving data. Several of these use fields the pipeline already collects.

Step-by-step

How to make the changes

Do the corrections first — they're mostly edits to panels that already exist and they make today's numbers trustworthy. Then layer the enhancements. Everything is in Kibana → Dashboards → Infra Dashboard Prototype → Edit; snippets below are the exact formulas and ES|QL to paste.

Phase 1 — Corrections make today's numbers trustworthy
Panel: Servers Up · Servers Down · Availability

C1 — Widen the window to 15 minutes and make it consistent

Edit each of the three availability panels and replace the 5-minute window. Use unquoted date math everywhere so the three panels match.

# Servers Up  — filter on the unique_count column
@timestamp >= now-15m

# Servers Down — formula
unique_count(host.name) - unique_count(host.name, kql='@timestamp >= now-15m')

# Server Availability % — formula
unique_count(host.name, kql='@timestamp >= now-15m') / unique_count(host.name)
Panel: Fleet Availability %

C2 — Rename the tile to "Server Availability %"

Open the metric panel, and in the formula column's Display name (the custom label) change Fleet Availability % to Server Availability %. Confirm it matches the "Servers Availability" section header above it.

Panels: availability trio · optional but recommended

C3 — Anchor the baseline so the % stops drifting

Today "monitored" is "any host seen in the current time range," so a wide picker inflates it (and inflates "down") with rebooted or decommissioned hosts. Anchor the denominator to a stable expected set. If your CMDB fields are populated, count only monitored, operational CIs:

# denominator, using CMDB attributes present on metrics-*
unique_count(host.name, kql='ci.is_monitored: true and ci.operational_status: "Operational"')

If CMDB isn't reliable yet, at minimum pin the dashboard time range (C9) so the number is defined and reproducible.

Discover → servicenow-incidents-* · then the P1/P2/P3 panels

C4 — Prove (or relabel) the incidents panel

In Discover, open servicenow-incidents-* and check for a CI / asset / category field — likely cmdb_ci, ci.name, u_host, or category. Then either scope the three panels to infrastructure, or relabel them honestly.

# if a CI field exists — add to each panel's KQL filter
priority_name : "1 - Critical" and cmdb_ci : *

# if no host/CI link exists — this isn't an infra panel:
# rename section to "ServiceNow Incidents (all priorities)" and relocate
Markdown panels: Oracle & MySQL "Detailed Dashboards"

C5 — Give the links real destinations and names

Edit both markdown panels. Replace the three identical tf0R3 links with the dashboards they're meant to open, named by function. If only one exists today, ship one link — don't pad to three.

### Oracle — Detailed Dashboards ###
[Tablespace & Sessions](https://kibana-prod.gcp.cna.com/app/r/s/<id-1>)
[Wait Events & Locks](https://kibana-prod.gcp.cna.com/app/r/s/<id-2>)
[Backup & Data Guard](https://kibana-prod.gcp.cna.com/app/r/s/<id-3>)
Sections: Oracle & MySQL

C6 — Populate the DB tiers, or drop them for now

Both sections currently show links only. Either add DB-tier panels (host CPU/mem for those hosts, plus DB metrics — connections, tablespace/buffer usage if collected) or hide the sections until the data exists, so the dashboard doesn't imply coverage it doesn't have.

Panels: Linux — CPU % and Memory % (ES|QL)

C7 — Make "Linux" mean Linux (or rename it)

The Linux tables match only redhat. Broaden to all non-Windows hosts (simplest robust definition), or rename the section to "RHEL Servers" if RedHat-only is intended.

FROM .ds-metrics-system.cpu-default*
  | WHERE host.os.family != "windows" AND system.cpu.total.norm.pct IS NOT NULL
  | STATS cpu_pct = AVG(system.cpu.total.norm.pct) BY host.name, host.os.family
  | SORT cpu_pct DESC
Panels: the four heat tables

C8 — Rename tables and clean stale columns

Each table still has the saved title Bar vertical stacked and duplicate cpu_pct/memory_pct column definitions. Rename to what it shows (e.g. "Windows — CPU % by host") and remove the unused columns so exports stay clean.

Dashboard settings → Save

C9 — Save a default range and turn on auto-refresh

Set the time picker to Last 1 hour, enable auto-refresh at 1 minute, then Save with "Store time with dashboard" ticked. This makes every viewer land on the same, well-defined range — which is also what makes the C1/C3 availability math reproducible.

Phase 2 — Enhancements turn it into an observability tool
Dashboard → Controls

E1 — Add a filter bar

Add Options list controls for relay.dc (datacenter), host.os.family, and ci.operational_status, plus a host.name search control. With chaining on, selections cascade to every panel — the fastest single win here.

New ES|QL table · top of dashboard

E3 — Add the "servers not reporting" list

Turn the "down" count into an actionable list. This finds hosts whose most recent metric is older than 15 minutes.

FROM .ds-metrics-system.cpu-default*
  | STATS last_seen = MAX(@timestamp) BY host.name, host.os.family, relay.dc
  | WHERE last_seen < NOW() - 15 minutes
  | SORT last_seen ASC
New ES|QL table · resource row

E4 — Add disk (and later, network)

Surface the fullest filesystem per host and flag anything above 80%. Same heat palette as the CPU/mem tables so it reads consistently.

FROM .ds-metrics-system.filesystem-default*
  | WHERE system.filesystem.used.pct IS NOT NULL
  | STATS disk_pct = MAX(system.filesystem.used.pct) BY host.name, system.filesystem.mount_point
  | WHERE disk_pct > 0.8
  | SORT disk_pct DESC
New Lens line chart · availability strip

E2 — Add availability & utilisation trends

Add a Lens line of hosts-reporting (unique_count of host.name) over a date histogram, and a CPU/mem trend. A trend shows whether you're heading toward an outage; the current single numbers can't.

New ES|QL table · service health

E7 — Surface stopped services / dead processes

The data is already flowing. List Windows services that should be running but aren't (and equivalently process.* / system.process.state for Linux daemons).

FROM .ds-metrics-windows.service-default*
  | WHERE windows.service.state != "Running"
      AND windows.service.start_type == "Automatic"
  | KEEP host.name, windows.service.display_name, windows.service.state
  | SORT host.name
New Lens metric · pipeline health

E9 — Monitor the monitor

Add a data-freshness panel: median ingest_lag_in_sec, agents-reporting vs. expected, and a count of error.message. With now-15m up/down logic, a stalled pipeline would otherwise look like a mass outage — this tells you which it is.

Elastic → Observability → SLOs & Alerting

E5 · E6 — SLO, thresholds, and incident context

Define an availability SLO (e.g. 99.9%) with an error-budget tile, add reference lines to the heat tables, and create alerting rules so breaches page someone. For incidents, add over-time-by-priority, open vs. resolved, MTTR/ageing, and top affected CIs.

Cross-cutting

E8 · E10 · E11 — CMDB grouping, fleet coverage, and polish

Group panels by ci.geo.name / business service and show owners; define the expected fleet once from CMDB so missing tiers appear as coverage gaps; and add the threshold legend, explicit units, and a "data as of" note (already sketched in the mock-up).

Suggested order of play. Ship Phase 1 as one change — it's low-risk and makes the current numbers honest (and closes your five notes). Then take Phase 2 in slices: E1 filters + E3 down-list + E9 pipeline health first (fast, high value), then E4 disk + E2 trends, then E5/E6 SLO & incident context once C4's data question is answered.
